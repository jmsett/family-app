# Foundation decisions and API contract

## ADR 021: Editable recurring planning with scoped corrections and full deletion

Owner explicitly authorized removing historical recurring planning data, while actual financial postings remain separate. Schema 9 adds `expenseChanges`, keyed by recurring expense ID and effective month. Each complete snapshot captures name, amount, due day, end date, category and labels. The original schedule retains its first-payment anchor and archive boundary. Select the latest applicable snapshot for each monthly plan; keep clamping due days and inclusive end dates. Historical chart goals already derive monthly plans and therefore reflect scoped corrections without altering cash flows.

Forward edits replace snapshots from the selected month onward, retaining earlier ones. All-history edits replace the timeline from the first payment month. The editor states the scope and that later scheduled changes will be replaced. Archived schedules stay archived. Delete removes the schedule and all snapshots from the current document and derived historical budgets; a prompt distinguishes it from archive and from immutable transfers/actual ledger entries. Git history and previous backups are outside this deletion. All operations stage in Monthly plan until its atomic save.

Validate change references, unique schedule/month pairs, positive integer-cent amounts, due days 1–31, metadata and original-date/end constraints. Include every effective change month in aggregate-limit validation. Group snapshots once per monthly projection to avoid repeated scans per schedule. Canonical serialization and decoding normalize change fields, and existing three-way plan conflicts cover edits/deletions. A stale financial-only device adopts the remote deletion while retaining immutable financial events; competing plan edits require review. Schemas 2–8 migrate to empty change history with no fabricated corrections, altered financial records or credential changes.

Verification covers scope/version replacement, month-end/end/archive boundaries, aggregate limits, historical charts, deletion retaining cash/ledger, malformed references/migration, stale-device sync, phone/desktop edit/delete forms and production offline/two-device workflows.

## ADR 020: Planned lump-sum trip costs alongside contingency

Owner requested an additional total for tours and other planned expenses. Schema 8 adds required integer-cent `TripGoal.otherMinor`; schema-7 trips migrate with zero to preserve previous budgets, allocations, labels and photos. Earlier migrations chain through that upgrade. Canonical serialization, decoding and sync include the field; old clients reject the newer schema rather than drop the planned amount.

Trip total = food for both travelers + hotel + both return fares + existing percentage/fixed contingency + planned other expenses. The new amount is a total for both travelers, added once with no day/person multiplier and no automatic contingency applied to it. Label existing allowance controls and breakdown as Contingency, display Other planned expenses independently, and preserve the new field on edit/reload. Test positive/invalid amounts, unchanged contingency, zero-default migration, phone/desktop forms and production offline/two-device synchronization.

## ADR 019: Travel goals earmark joint savings

Owner clarified that goals use the joint confirmed savings fund, with one goal progress bar. Schema 7 adds `trips`: stable ID/name/label, optional date pair, estimated duration and hotel nights, cent-denominated food/hotel/return flights/extras, percentage-or-fixed extras mode, planned total allocation, optional small JPEG and archive state. Budget uses two travelers, inclusive food days and independently editable hotel nights. Name-derived labels include an ID suffix, stay stable through rename/archive and are retained by storage/sync. Schemas 2–6 migrate to an empty trip list, preserving all existing money/income/identity/credential stores.

Allocations are mutable earmarking plans, not new cash, transfers or ledger events. Available allocation = recorded savings less active remaining trip reserves. Each reserve = max(0, planned allocation minus active savings-funded expenses with that trip label). A purchase consumes the reserve and cash once, while its immutable reversal restores both. A savings-funded expense may reference at most one trip label. Personal/operating expenses do not use pooled savings. Goal progress is total allocated divided by budget, including amounts paid from savings; the details disclose remaining reserve and actual savings-paid amount. Increases cannot exceed available savings or the goal budget. Later withdrawals/retracted contributions remain valid financial history; warn of a reservation shortfall and disallow further increases. Archiving releases the reserve and preserves labels/expenses; restoring starts with zero allocation.

Trip configuration uses the existing three-way plan conflict protocol. Concurrent offline allocations, even on separate trips, stop for review. Explicit remote-plan recovery retains local goals missing from the selected remote plan as archived, zero-allocation identities, avoiding dangling historical labels without silently restoring discarded reservations. Conflicting same-ID labels are rejected. Immutable funding and ledger merging remains separate.

The airplane page supports optional photos, in-browser resize/re-encode into metadata-free JPEG (60k data-URL characters each, 300k aggregate), private JSON storage/sync and pre-save JSON-size checks against the existing 1 MB envelope. No public photo server or destination-price requests. Extras default to editable 15% or an exact amount; [travel-budget guidance](https://navyfederal.practicalmoneyskills.com/en/learn/budgeting/situational-budgeting/travel.html) recommends 10–15% for unexpected costs. Known transport, activities, insurance and baggage should be budgeted explicitly. Dated goals show an indicative monthly saving pace.

Expense entry offers trip labels; the trip shortcut opens all-date history and category spending filtered by label. Existing filters remain collapsed. Explicit Home navigation clears shortcut context. Use the existing appearance-aware savings progress bar and Android touch targets; hide the brand at the narrowest widths to fit six 48-pixel icon controls. Two fictional goals join the isolated demo data. Verification covers dates, allocation conservation/consumption/reversal, conflicts, migration, photo upload/persistence, archive/restore, labels, phone widths and production offline/two-device synchronization.

## ADR 018: Effective incomes, equal lower-income funding and home scenarios

Schema 6 adds `incomes` (month and a pair of net monthly cent amounts) and `fundingRules` (effective month, fixed/income mode and operating/leisure/savings basis points totaling 10,000). Both carry forward. Schemas 2–5 migrate to empty histories, retaining the original recurring/fixed method and all financial events, revisions, credentials and identity. Canonical serialization and decoding include both histories; synchronization treats them as plan settings with three-way conflict detection. The owner confirmed equal contributions based on the lower income. Each shared-fund share is floor(minimum income × basis points / 10,000), and the target is twice that amount. Leisure is personal guidance, not a new fund. A zero income implies zero equal targets. Recurring forecasts stay visible with shortfall/headroom; they are not inflated to match funding. Recorded confirmations remain captured amounts and fund charts derive goals from each historical month’s rule/income.

Settings collects effective-month income; Investments shows the selected month × 12 as estimated annual income, excluding bonuses/extra salary. A second panel shows home affordability with collapsed budget and loan assumptions. Defaults use the owner’s 30–35% net income caps, €350–500 ownership costs and 3–5% illustrative rates, plus editable other debts, 30-year full amortization, zero upfront cash and 10% purchase costs. Derive principal from the annuity present-value formula (linear at zero interest), then price = (principal + cash)/(1 + purchase-cost rate). Clamp negative loan budgets to zero and validate all ranges before displaying a result. Conservative pairs lower budget/higher costs/higher rate; optimistic does the reverse. A rate sensitivity graphic retains both budget bounds. Insufficient cash for purchase costs explicitly assumes financing the gap. These are local what-if assumptions, not live quotes, local tax advice or lender underwriting; they do not consume recorded savings. Store validated assumptions in a separate device key; sample mode uses its own key.

A deterministic fictional schema-6 JSON provides 23 months of chart data. Dynamic import keeps it outside the initial bundle, while the PWA precaches the chunk. `?demo=1` initializes an in-memory household and identity, commits in memory, mounts no SyncPanel and never calls real household storage or restores a GitHub token. Reload resets sample edits; returning to the normal URL restores the real household. No generic JSON import or real-repository write is needed to test charts. Appearance remains a separate device preference. Tests compare real IndexedDB contents before/after sample edits and cover first sample visit offline.

References: [CFPB affordability assumptions](https://www.consumerfinance.gov/owning-a-home/prepare/decide-how-much-you-want-spend/) (ownership costs, term, down payment; US-specific regulatory content is not applied as local rules).

## ADR 017: Audited funding retractions and reconfirmation

Owner requested tapping a confirmed checkmark again to retract a mistaken funding declaration. Schema 5 retains each immutable confirmation and adds `transferRetractions`, keyed `retract:<confirmationId>` with the target, member and timestamp. Each confirmation has a generation: zero retains the schema-4 `month:member:fund` ID; subsequent IDs append `:generation`. A new generation requires its immediately preceding confirmation and retraction. At most one generation per member/month/fund can be active. Migration from schemas 2/3/4 preserves amounts, timestamps, ledger and revision; existing fund records become generation zero with an empty retraction list. IndexedDB version, saved credentials, identity and appearance remain unchanged. Older clients reject the newer schema rather than overwrite it.

The selected member can retract their own fund confirmation after a prompt. Automatic zero-responsibility checkmarks remain disabled. Active confirmations alone determine monthly status, cumulative funds and chart changes. A retraction restates the original funding period; it does not create spending, debt or a withdrawal. Reconfirming captures the current target as a new immutable record. Fund activity retains both originals and retraction captions. Existing expenses/payments/movements remain recorded even if retraction leaves negative available funds.

Sync unions confirmations and canonical retractions independently of plan settings. Duplicate retractions select the earliest timestamp. Stale confirmations cannot resurrect funding, and a retraction of an earlier generation cannot cancel a later one. Identical concurrent confirmations in the same generation deduplicate; differing amounts stop for review. Local persistence and remote plan recovery retain both confirmation and retraction history. Stable field ordering preserves idempotent content comparisons after decoding.

Verification covers schema migration, cycles and invalid references, active totals and chart restatement, retries and concurrent/stale-device merging, cancelled prompts, fund/member isolation, desktop/Android reload, production offline use and two-device mocked GitHub synchronization. Physical Android and real private-repository interaction remain owner checks.

## ADR 016: Monthly funding comparisons, native value scaling and category pie

The owner requested combining the budget and funds views. Fund-history points now carry derived `fundedMinor` and `targetMinor` alongside the available balance. Confirmed contributions are counted by assigned month and effective confirmation date; payments, spending and movements never increase that monthly funding figure. Available money still carries all earlier cash flows and reserves household liabilities. Overlaid curves, legend, status and the accessible value table compare cumulative availability with confirmed funding and the goal for the month ending each interval. Monthly funding resets at the boundary while balances carry forward. This retains the explicit ending-month convention for weekly/yearly intervals; it does not imply annual funding totals. The standalone operating-budget selector is removed; no persisted schema changes are needed.

Enable `axisPressedMouseMove.price` for native value-axis dragging. Lightweight Charts also gates touch-axis gestures on `handleScroll.vertTouchDrag`; use capture-phase hit testing against the public right-axis width to enable that flag only for a gesture beginning on the value axis. Restore the default on end/cancel. This preserves vertical page scrolling in the plot, horizontal pan/pinch, and an unchanged time range during value scaling. Reset value scale and All re-enable automatic value fitting. Advanced options exposes the value range for accessible inspection.

Monthly planning separates recurring costs, fixed savings and contribution totals into independent panels while sharing the existing draft, validation and atomic save. Overview category spending now uses code-native SVG pie slices plus an accessible exact amount/percentage legend, the existing category palette and filters. Handle the single-category case with a full circle; empty ranges show no invented slices. Reversals/repayments retain the existing actual-spending rules.

## ADR 015: Read-only historical explorer and separated overview panels

Owner requested the explorer after the compact funding pass. Keep schema 4 and all persisted financial events unchanged. `history.ts` derives integer-cent series in a linear pass over sorted dated fund changes and intervals, carrying opening balances from before the selected range. Active expenses contribute category spending; fund contributions, account-specific expenses/settlements and fund movements change their corresponding pools; household net debt reserves operating availability. Reversals cancel original entries in their original period. Expense points are period sums; savings/operating points are end balances; budget points sample the monthly operating target at period end, including forecasts. Yearly budget points therefore remain monthly targets, not annual totals. Monday weeks and partial first/last intervals are explicit.

Contribution records contain assigned month and confirmation timestamp, without an independently recorded bank-payment date. Use Europe/Busingen local confirmation dates inside the assigned month; clamp early/late declarations to the nearest assigned-month boundary. This reconciles the existing monthly Overview contract while making the daily convention explicit under Advanced options. Do not claim verified historic bank balances. Blank histories remain blank/zero records rather than chart demo data.

Use TradingView Lightweight Charts 5.3 for client-only histogram/line rendering and native mobile pinch/horizontal pan, wheel zoom and crosshair inspection. Visible controls are series, bars/line, D/W/M/Y, zoom and All fit; Advanced options contains range/category/grid and paginated accessible exact values. Keyboard navigation and a labeled chart group supplement the visual canvas, which is hidden from assistive technology in favor of the readout/table. The dynamic chart chunk, Apache-2.0 notice/license and fancy-canvas MIT license are static build assets cached for first-use offline access. A visible TradingView attribution link is retained. No household data or market requests go to TradingView.

Home/calendar/chart/settings icon buttons retain accessible names, current-page state and touch sizes. Overview removes duplicate personal/member balances, marks the selected member “you”, centers fund values within their grid row, adds monthly total/own-share captions and concise confirmations, and places history/category details in distinct panels. Existing unsaved-form protection applies when switching to Charts.

## ADR 014: Independent funding, fund movements and compact personal history

Schema 4 replaces each combined member/month contribution with one immutable confirmation per `month:member:fund`, carrying fund, captured amount and confirmation timestamp. Migration from schemas 2/3 splits only positive recorded amounts and preserves the ledger, revisions, baseline, saved credentials and preferences. No cash is inferred from a target. Zero responsibility completes the checkmark as not required without a financial entry. Separate fund declarations can merge from different devices for the same member, while conflicting amounts for one fund stop synchronization. The UI still plans 50/50 contributions; future unequal shares must apply by effective month without rewriting past confirmations.

Add immutable `fund-movement` events between operating/savings or from either to external untracked funds, with amount, effective date, recorder, timestamp and description. These events do not change personal debt or category spending. Original-period reversals cancel them once. Household-funded expenses and household settlements optionally specify their fund (legacy/default operating); personal-source entries cannot name a household fund. Cumulative balances start with confirmed contributions, apply account-specific purchases/repayments and movements, then reserve net household liabilities from operating funds. Recorded balances may be negative if records exceed funding; these remain trusted accounting declarations rather than verified bank balances.

Basic expense inputs are quick setup, description, amount, category and labels; advanced inputs collapse. Both members’ payer perspectives are available without changing the recorder. Equal presets include the two members; Household participation is optional in advanced settings. History rows show original signed net effect on the selected member, including inverse effects for reversals, while all-time net balances include repayments. Repayment Details explicitly distinguish debt reduction from income. Details and Filters collapse independently; category bars retain the appearance palette. Positive/negative signs supplement fixed JML cyan/orange colors, with a contrasting backing in light mode.

Funds have cumulative values and fund-specific member/month checkmarks instead of progress bars. Checkmarks confirm only the selected device member’s full fund transfer; another person’s expenses remain recordable under trust. Contribution history and movement entry collapse under Fund activity. Unsaved movement and expense forms protect navigation and block foreground sync. The historical explorer is a separate next pass: shared touch navigation, daily/weekly/monthly/yearly intervals, summed spending versus end-of-period balances and clearly separate budget targets.

## ADR 013: Immutable expenses and three-party settlements

The owner approved a Splitwise-style ledger for members A/B and Household, above Member transfers on Overview. Schema 3 adds `ledger: LedgerEvent[]` to `household.json`. Schema-2 readers upgrade to an empty ledger while preserving every existing field; IndexedDB stays at version 2 because the household store already supports the document. Old clients reject schema 3. Tokens and appearance remain in their existing separate stores. Device identity moves into the top-right Settings cog, remaining a trusted local selection rather than authentication.

An expense has immutable ID, effective date, timestamp, actor, description, payer, personal/household funding source, amount, split mode/input/allocated cents, category and labels. Credit the effective funding party and debit each beneficiary; balances sum to zero. Equal splits allocate by inclusion, exact splits must total the amount, and percentage weights must total 10,000 basis points. Largest-remainder rounding preserves every cent deterministically. A household-funded expense uses Household as funding party regardless of who physically made the payment. Recurring plans never become actual purchases automatically.

A settlement credits its sender and debits its recipient, reducing debt without increasing actual spending. Net debtor/creditor matching requires the minimum one or two transfers for exactly three parties. Also permit outstanding direct claims, bounded so a payment cannot turn the outstanding debt into an overpayment. Suggestions do not send money. Reversals cancel an expense/settlement once, and corrections atomically add reversal plus replacement. A reversal retains its original effective date while its timestamp/actor/reason document the correction. Original entries cannot be removed or edited locally, by sync, or during plan recovery.

Recorded operating pool through a month = confirmed operating contributions − household-funded purchases − outgoing household repayments + incoming household repayments. Usable operating funds additionally reserve max(0, −net Household balance). This avoids counting a personal advance once at purchase and again at reimbursement. Savings accumulate confirmed savings contributions separately. Both envelopes carry forward; monthly transfer status and funding progress remain month-specific. These are recorded virtual funds, not verified bank balances. All-time debt stays visible regardless of report/month filters.

Synchronization unions immutable IDs and rejects mismatched payloads. Replacement expenses reference their corrected original; competing active replacements in the same correction lineage stop sync instead of counting both. Reverse one incorrect replacement before retrying. Independent purchases and affordable partial repayments merge; retries deduplicate. Concurrent unique active repayments are checked deterministically against the merged debt before any upload. Overpayment conflicts preserve device/remote copies for review; reverse an incorrect device payment to resolve, then retry. Reversal records remain even if another device also reversed the same original; economics cancel the original only once. Plan config still uses three-way conflict detection, with existing revision and GitHub SHA guards.

History and actual category charts share date/party/category filters and exclude repayments and reversed expenses from spending. Categories use the existing device palette. Generic JSON import, authenticated member identity, contribution-confirmation corrections, goals, bank matching and month close remain outside this pass.

## ADR 012: Separate PWA installation identity

Both Family and Nunz previously used manifest `id: "./"`. Unlike `start_url`/`scope`, a relative `id` resolves against the start URL's origin, so both advertised `https://jmsett.github.io/`. This can collide with an already installed application. Family now declares explicit `id`, `start_url` and `scope` values of `/family-app/`. Nunz is not modified. Keep this identifier stable across future icon and palette changes. The HTML links a versioned manifest URL so older workers bypass their previously cached manifest; the new worker normalizes query strings only for known built assets, keeping the versioned manifest available offline. Browser tests assert the resolved Family identity is `/family-app/`, not the shared origin root. No household, credential or appearance storage is cleared by this fix.

## ADR 010: Remember device connections as Nunz does

Owner feedback requests the connection behavior already used by `nunz-app`. After validating private-repository access, store the token in database `family-github-device-v1`, store `secrets`, key `github-token`. This database is separate from household data and excluded from all sync documents, exports and public assets. Restore it on app start, allowing automatic foreground synchronization without re-entry. Disconnect deletes the saved token and preserves household records. Other open app tabs receive a credential-change notification without broadcasting the token itself.

This is browser storage, not an encrypted OS credential vault; same-origin scripts can access it. Expiration, revocation or clearing browser data requires reconnecting. Invalid tokens are not persisted. Existing household data/schema is unchanged.

## ADR 009: Recurring planning and trusted transfer confirmations

Owner feedback replaces the editable total allocation and configurable split with derived monthly operating costs, fixed savings and a 50/50 split. Recurring schedules store first due date, optional inclusive end date, archive effective month, category and labels. Savings targets carry effective-month history. Overview contains confirmed funds, while all target definition lives in Monthly plan.

This earlier slice introduced `HouseholdPlan` schema 2 (upgraded by ADR 013) at private `household.json`. IndexedDB version 2 adds the `household` store, preserving old `budgets` rows. Migration preserves original manual drafts in `legacyDrafts`; operating targets are not converted into fake expenses. Existing savings targets carry forward as plans. When no remote household exists, the adapter migrates old private monthly JSON without deleting it. ADR 007's per-month data shape is superseded.

Confirmation IDs are `YYYY-MM:memberIndex`. Each member declares the full displayed operating/savings transfer once per month; captured amounts never change after plan edits. The client uses a self-selected member with a clear trust label, not authenticated member identity or bank evidence. Partial payments, top-ups, reversals and statement matching require future work. Forecast schedules do not post actual expenses.

Sync uses a three-way comparison of plan settings, unions immutable confirmations and deduplicates same-member/month declarations with matching amounts. Mismatched amounts require review. Remote recovery retains confirmations; the storage transaction rejects removing/changing recorded amounts. Whole-household exports include schedule/history/confirmation records, never credentials. ## ADR 007: Implemented device and GitHub draft contract

The static app uses IndexedDB database `family-manager-v1`, object store `budgets`, keyed by month. Each entry includes the current draft, last remote baseline, remote blob SHA and pending flag. Local compare-and-write uses one read/write transaction, preventing stale tab saves. Local revisions invalidate forms after remote replacement. A synchronization failure never clears pending changes.

Remote path: `budgets/YYYY-MM.json` on `main`; envelope `{ schemaVersion: 1, draft: BudgetDraft }`. The client validates the schema, selected month, integer amounts and names before applying records. Each cycle checks repository privacy. Updates recheck privacy and include GitHub's current SHA; divergent changes against the baseline require manual review. Matching local/remote content acknowledges a retry after a lost response. Deletion of a previously synchronized file is an explicit error.

Initially tokens lived only in component memory; ADR 010 supersedes that choice. No application login/passkeys or per-member data access controls are implemented. Repository scope grants access to all records; finer access boundaries need separate review. GitHub API responses bypass the service worker; only build-generated static assets enter its cache. Cache versions depend on build content, and scope-specific prefixes avoid deleting other applications' shell caches. IndexedDB remains shared by same-origin pages.

The API contract and decisions below describe the legacy server prototype. It remains available for development; the browser uses this device contract in production.

## ADR 008: Branch deployment matching Nunz

The owner chose **Deploy from a branch → main → /(root)**. `npm run build:pages` builds the PWA for `/family-app/` and copies browser-ready files from `apps/web/dist` into the repository root. `.pages-files.json` identifies generated artifacts, allowing the preparation script to delete obsolete build files while preserving source and documentation. `.nojekyll` bypasses Jekyll. Generated bundles are excluded from lint/formatting; CI rebuilds and checks their Git diff to catch stale public assets. GitHub's standard branch Pages workflow publishes the committed build. The custom Pages deployment workflow is removed. Only public app assets are copied; credentials and private repository data never enter the build.

## ADR 001: Virtual funds and money

Accepted for M0 implementation, subject to owner review. One household currency (EUR), two proposed contributors, Europe/Busingen timezone. Targets, commitments, self-reported earmarking, actual expenses, payables and forecasts are separate concepts. M0 implements **targets only**; recorded totals are explicitly zero, since no financial-entry capability exists yet. Never infer bank balances. General savings is included in the total allocation. Default categories: Groceries, Home & bills, Transport, Health, Leisure, Other.

Amounts are integer minor units, capped at €1,000,000 in the prototype. Decimal user input is parsed as strings, including comma decimal separators, without floating-point currency calculations. Shares use integer basis points summing to 10,000. Member A rounds down and B receives any remaining cent. Changing a monthly draft never changes another month.

## ADR 002: Ledger and storage boundary

SQLite is authoritative; React holds only current form state, with no offline cache yet. `budget_drafts` stores the current proposal; `draft_audit` appends each accepted revision in the same immediate transaction. Revision checks reject stale writes with HTTP 409. Drafts are editable proposals, not ledger transactions. Schema migration version 1 runs idempotently at startup; future migrations must be numbered, transactional and tested against existing versions.

M2 will add balanced, immutable ledger postings and corrections by reversal. Member-held household funds and personal advances must use distinct sources. Repayments settle liabilities, never create a second expense; savings transfers move envelopes, never create money. Financial idempotency and authorization must precede financial endpoints.

## ADR 003: Local boundary and planned sessions

M0 is an unauthenticated local planning prototype. Servers default to 127.0.0.1; API checks loopback Host values and allows writes only from configured local origins (nonbrowser requests without Origin are allowed). No permissive CORS. No LAN or VPN deployment until M1. In Docker the process binds all container interfaces, but Compose publishes the host port only to 127.0.0.1. This is a development boundary, not member authentication.

M1 will implement invite-only passkeys with a maintained WebAuthn library, server-side revocable sessions and Secure/HttpOnly/SameSite cookies, authorization on every household route and a tested recovery path. No default password or public signup. Two authenticators per member where feasible. Enrollment and recovery design must be reviewed before implementation is called ready.

## ADR 004: Stable HTTPS relying party

Keep localhost for same-computer development. Before phone enrollment, choose a stable private HTTPS hostname with the owner (prefer local PC + Tailscale Serve). RP ID must match that domain; migrations to a different RP domain require explicit re-enrollment planning. VPN presence never replaces app authentication. M0 does not register passkeys or cache financial data.

## ADR 005: Backup policy

Prototype drafts live in ignored `data/`. The volume is persistence, not a backup. Production backups in M8 must use SQLite online backup or VACUUM INTO, include controlled image uploads and schema metadata, encrypt archives, keep an off-device copy and test restore including login. Do not copy a running WAL-mode database as a single file. Avoid committing private plans, data, environment secrets or tool installations.

## M0 HTTP contract

All responses are JSON except static web files. All API data is development-only and unscoped until M1 adds membership.

| Method and path                    | Request                                                                                         | Success                                         | Failure                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------ |
| GET `/api/health`                  | None                                                                                            | 200: status, schemaVersion, mode                | 503/network if unavailable                             |
| GET `/api/workspace?month=YYYY-MM` | Optional month, defaults to current household month                                             | 200: Workspace (see shared TypeScript contract) | 400 invalid month; 403 unsupported Host                |
| PUT `/api/budget-draft`            | BudgetDraft: month, totalMinor, savingsMinor, two memberNames, firstMemberBasisPoints, revision | 200: Workspace with incremented revision        | 400 invalid input; 403 origin/Host; 409 stale revision |

An unsaved month has revision 0 and a clearly marked example proposal. Writes require the last read revision. Stale drafts must be reloaded and reviewed manually; no automatic overwrite. These endpoints intentionally do not post real money. `DB_PATH` selects storage, `PORT` defaults to 3001. Static production assets are served from `apps/web/dist` after building; Vite proxies `/api` during development.
